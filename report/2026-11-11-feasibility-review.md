## 결론과 근거

대상 앱과 작업을 제한한 시각적 튜토리얼은 구현 가능성이 높다. 임의의 모든 앱·현실 기기를 사전 정보 없이 정확하게 안내하는 범용 제품은 별도의 장기 목표다. 기술적 데모 가능성과 실제 고령자에게 도움이 되는 제품인지는 각각 검증해야 한다.

Electron은 화면 소스 캡처와 마우스 이벤트를 통과시키는 창을 지원한다. 따라서 데스크톱 캡처와 오버레이 자체는 기존 API로 구성할 수 있다. OS 권한, 전체 화면, 다중 모니터, 배율, 포커스는 별도 통합 시험이 필요하다. [화면 캡처](https://www.electronjs.org/docs/latest/api/desktop-capturer/), [클릭 통과 창](https://www.electronjs.org/docs/latest/tutorial/custom-window-interactions)

Chrome 확장의 content script는 페이지 DOM을 이용할 수 있고 Windows UI Automation은 접근 가능한 UI 요소와 이벤트를 제공한다. 이런 구조 정보를 우선하고, 제공되지 않는 영역에 OCR·CV를 보완적으로 쓰는 방식을 권장한다. 모든 앱이 같은 수준의 정보를 노출하는 것은 아니다. [Chrome 문서](https://developer.chrome.com/docs/extensions/develop/concepts/content-scripts), [Microsoft 문서](https://learn.microsoft.com/en-us/windows/win32/winauto/uiauto-uiautomationoverview)

OmniParser는 스크린샷을 구조화된 UI 요소로 파싱하는 구현 사례다. ScreenSpot-Pro 연구는 고해상도 전문 앱에서 작은 목표 요소를 찾는 문제를 다룬다. 이 자료는 접근 가능성의 근거이며, 특정 모델의 현재 성능이나 우리 제품의 성공률을 보장하지 않는다. 기존 연구 수치를 2026년 최신 성능으로 간주하지 않는다. [OmniParser](https://github.com/microsoft/OmniParser), [ScreenSpot-Pro 논문](https://arxiv.org/abs/2504.07981)

## 방식별 범위

| 범위 | 판단 | 주요 제약 |
| --- | --- | --- |
| 지원 웹사이트의 단계별 안내 | 첫 MVP에 적합 | DOM 접근 권한, UI 변경, iframe/canvas 등 |
| 특정 데스크톱 앱의 화면 오버레이 | 구현 가능 | OS 권한, 배율·좌표, UI 구조 접근성 |
| 임의의 모든 앱에 대한 자동 안내 | 초기 품질 보장 어려움 | 작업 지식, 숨은 상태, 예외와 버전 다양성 |
| 휴대폰 카메라 영상 위 키오스크 안내 | 제한 환경 PoC 가능 | 반사·기울기·흔들림·가림·촬영 부담 |
| 스마트 글래스의 실제 버튼 위 AR 표시 | 기기별 추가 검증 필요 | 표시 장치, 카메라 접근, SDK, 시점 보정·추적 |

일반 웹페이지에서 다른 앱 전체를 덮는 OS 오버레이를 제공하는 것으로 설계하지 않는다. 브라우저 내부 안내와 데스크톱 앱 안내는 배포 방식이 다르다. Android 화면 공유도 세션별 동의 등 제약이 있으므로 백그라운드 실행을 무제한·무권한 감시로 해석하지 않는다. [Android MediaProjection](https://developer.android.com/media/grow/media-projection)

## CV의 역할 및 권장 처리 흐름

사용자 목표 → 허용된 화면 관찰 → UI 요소와 현재 상태 추출 → 검증된 절차 및 지식에서 다음 단계 선택 → 대상 위치 확인 → 한 단계 안내 → 화면 변화와 성공 조건 확인 → 다음 단계 또는 복구.

- OCR: 글자와 위치 인식. CV: 버튼·아이콘·화면 경계 인식, 카메라 좌표 보정과 추적. 멀티모달 모델: 화면의 의미와 목표 해석. 상태 관리: 진행 단계와 완료 조건 유지.
- 범용 모델이 직접 좌표와 명령을 자유롭게 생성하는 구조보다, 관찰된 요소 ID 중 다음 대상을 선택하고 렌더러가 실제 좌표를 매핑하는 구조를 우선 실험한다.
- 단계마다 목표 요소, 설명, 사전 조건, 완료 조건, 실패 시 복구 방법을 둔다. 규칙/상태 전이로 절차를 관리하고 AI는 목표 해석과 설명 개인화 등에 사용한다.
- 클릭 자체를 완료로 간주하지 않는다. 다음 화면, 장바구니 항목, 실행 결과 등으로 확인한다. 관측할 수 없으면 사용자 확인을 요청한다.
- 화면 변경 후 기존 좌표를 무효화한다. 창 이동, 스크롤, 확대, 다중 모니터에 대응한다. 자체 안내 화면이 인식 입력에 반복 유입되지 않도록 한다.
- 모델의 자기보고 신뢰도만 믿지 않고 요소 존재 여부, 상태 일치, 실제 평가 결과로 안내 여부를 결정한다. 대상이 불명확하면 강조를 멈추고 재관찰한다.
- 로컬 이벤트/화면 변화 감지와 추적은 빠르게, 고비용 의미 추론은 필요한 순간에 수행한다. 영상의 모든 프레임을 원격 모델에 보내는 구조는 초기안으로 권장하지 않는다.

기술 후보는 웹 확장 또는 Electron+TypeScript, 필요 시 Python 기반 CV 서비스, OCR, 멀티모달 모델, 상태 전이 엔진이다. 현재 모델 공급자·버전·요금이나 스택은 선정하지 않았다. 초기에는 자체 모델 학습보다 기존 구성요소 평가를 우선한다.

## 두 예시의 차이

React/FastAPI 시작 안내에는 화면 외에 실제 프로젝트 파일, 의존성, 실행 스크립트, 환경과 오류가 필요하다. VS Code 화면만 보고 실행 방법을 단정할 수 없다. 확장 기능으로 허용된 workspace 정보를 읽는 접근이 유리하다. 명령의 목적과 기대 결과까지 설명해야 학습 도우미로서 의미가 있다. [VS Code workspace 확장](https://code.visualstudio.com/api/advanced-topics/remote-extensions)

키오스크에서는 메뉴 선택·옵션·장바구니·결제 화면 등 상태 전환이 핵심이다. 외부 카메라로 관찰하면 내부 상태를 직접 읽을 수 없고 실제 결제 성공 역시 영상만으로 보장할 수 없다. 모의 주문과 결제 직전까지를 초기 범위로 제안한다. 키오스크 본체에 오버레이를 띄우려면 운영사 연동/설치 권한이 필요하고, 휴대폰으로 찍는 경우 안내는 휴대폰 화면에 표시된다.

## 카메라와 스마트 글래스

평면 화면은 화면 경계를 검출해 원근 보정하고, 보정된 좌표를 촬영 영상 좌표로 되돌려 박스를 표시하는 접근이 가능하다. 흔들림과 가림으로 추적이 깨지면 안내를 숨기고 다시 위치를 잡는다. [OpenCV homography](https://docs.opencv.org/4.5.5/d9/dab/tutorial_homography.html)

카메라 영상 위의 2D 박스와 실제 시야 속 버튼 위에 고정되는 AR 박스는 다른 구현이다. 후자는 기기 위치·시점과 공간 추적까지 필요하다. ARCore의 anchor 문서는 환경 추정이 갱신될 때 가상 객체의 위치를 유지하는 구조를 설명한다. 특정 글래스의 지원 여부는 장치 선정 후 확인해야 한다. [ARCore anchors](https://developers.google.com/ar/develop/anchors)

휴대폰 촬영은 고령자에게 한 손으로 기기를 들고 다른 화면을 조작하는 부담을 줄 수 있다. 글래스도 착용·초기 설정 부담이 있으므로 하드웨어 확장이 곧 사용성 향상이라고 가정하지 않는다.

## 사용자 경험 및 정보 처리

고령자는 시력·청력·운동·인지 능력과 디지털 숙련도가 다양하다. 한 단계씩 큰 글씨로 안내하고, 색상 외에 테두리·번호·문구를 함께 사용한다. 음성은 켜고 끌 수 있게 하고, 반복·뒤로·중지 기능과 충분한 대기 시간을 제공한다. W3C 자료는 이러한 사용자 요구와 접근성 기준의 연관성을 설명한다. [W3C 고령 사용자 안내](https://www.w3.org/WAI/older-users/)

제품 특성상 화면에 개인정보·비밀번호·결제 정보가 들어올 수 있다. 선택한 창/영역만 수집하고, 원본 화면의 기본 비저장, 전송 전 마스킹, 종료 시 캡처 중단을 설계 후보로 둔다. 화면 속 외부 문구는 관찰 데이터로 취급하며 앱의 지시로 실행하지 않는다. 초기 MVP는 안내 중심으로 하며 결제·삭제·명령 실행 자동화는 범위 밖으로 제안한다.

## MVP와 검증 단계 제안

고령자 지원이라는 우선 목표를 기준으로, 첫 MVP는 한국어·단일 환경·제한된 주문 흐름의 키오스크 안내가 적합하다. 개발자 도우미는 별도 후보로 유지한다.

| Phase | Sequence | 검증 내용 |
| --- | --- | --- |
| 0 | 1. 대상 사용자/기기 선정 → 2. 작업 흐름·실패 사례 수집 | 실제 어려움과 안내 필요성 확인 |
| 1 | 1. 키오스크 시뮬레이터 → 2. 한 단계 강조와 음성 → 3. 상태 전이·복구 | 안내 UX 검증. DOM 기반 성공을 CV 성공으로 보고하지 않음 |
| 2 | 1. DOM 없이 스크린샷만 입력 → 2. OCR/CV로 위치 찾기 → 3. 여러 레이아웃 평가 | 인식·절차 선택·완료 감지 각각 측정 |
| 3 | 1. 휴대폰 영상 → 2. 원근 보정/추적 → 3. 반사·가림 환경 테스트 | 카메라 도입의 추가 오류와 사용자 부담 측정 |
| 4 | 1. 실제 운영 환경 협의 → 2. 기기 선정 → 3. 현장/글래스 시험 | 배포 가능성과 실제 독립 사용 검증 |

개발자 튜토리얼을 먼저 선택한다면 Phase 1~2를 '한 OS + VS Code + 특정 프로젝트 유형 + 최초 실행 한 작업'으로 대체한다. 두 제품을 동시에 MVP로 만들지 않는다.

제안 평가 방법:

- 초기 사용자 5~8명 대상 형성 평가로 혼란과 실패 원인을 찾는다. 통계적 효과 입증용 표본으로 해석하지 않는다.
- 같은 난이도의 과제에서 안내 없음/일반 설명/시각적 안내를 비교한다. 순서를 바꾸어 학습 효과를 줄인다.
- 목표 위치 정답률, 다음 단계의 적절성, 잘못된 완료 판정, 안내 보류율, 작업 완수율, 도움 요청, 재시도, 소요시간을 분리 측정한다.
- 초기 내부 목표 예시: 제한 시나리오 완수율 90% 이상, 표시한 대상의 정확도 98% 이상, 안정된 화면 관측부터 안내까지 p95 3초 이내. 보류한 사례까지 포함한 전체 시도 수도 함께 보고한다. 이 수치는 실측·보장·출시 기준이 아니다.
- 창 이동·배율·스크롤·팝업·잘못 누름·네트워크 단절·반사·가림을 평가에 포함한다. 불확실할 때 중지와 복구가 되는지 확인한다.

## 일정·비용의 판단 범위

경험 있는 개발자 1명이 기존 모델을 이용하고 한 환경에 집중한다는 가정에서, 제한된 데모는 2~4주, 사용자 평가 및 실패 복구를 포함한 좁은 MVP는 추가 4~8주 정도를 초기 계획 가설로 둘 수 있다. 인력·숙련도·디바이스·지원 대상이 미정이므로 확약 일정이 아니다. 범용 앱 지원과 스마트 글래스 현장 제품은 별도 산정이 필요하다.

운영비는 세션 수 × 세션당 추론 횟수 × 요청당 비용에 음성·서버·저장 비용을 합산해 평가한다. 모델·해상도·호출 빈도가 미정이므로 금액은 제시하지 않는다. 지연과 비용은 실제 요청 로그로 측정한 뒤 판단한다.

## 제품 차별성과 미확정 결정

WalkMe 등 기존 제품도 앱 위 단계별 가이드를 제공한다. 따라서 시각적 가이드의 존재 자체보다, 사전 제작이 적은 환경 적응, 사용자 행동 후 완료 확인과 오류 복구, 고령자 대상의 실제 완수율 개선이 차별화 가설이다. 경쟁사의 전체 기능이나 시장 수요를 검증한 것은 아니다. [WalkMe 기술 소개](https://www.walkme.com/technology/)

다음 결정은 첫 사용자군(고령자/개발 입문자), 지원 환경, 첫 번째 완료 과제, 인력·기간·예산이다. 이 결정 전에는 DEV_PLAN과 ARCHITECTURE의 확정 내용을 작성하지 않는다.

## 검증 결과 및 제한

공식 API 문서와 연구로 구성요소의 존재와 접근법을 확인했다. 코드 구현, 모델 벤치마크, 실제 키오스크·글래스 테스트, 사용자 실험은 수행하지 않았다. 문서 검토 시 git status는 현재 폴더가 Git 저장소가 아니라는 오류를 반환했다. 파일은 저장했으며 commit/push는 수행하지 않았다.
